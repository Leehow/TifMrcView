# Native NAD 3D / EED

The Pro NAD option runs Rust inside the application. `nad_eed.rs` owns the numerical kernel; `denoise_nad.rs` reads the selected C/T volume, converts K from full-volume population SD, performs filtering, and retains one disk-backed result for preview and export. It never locates, links, or launches IMOD. The pre-existing 2D Perona–Malik option remains a separate algorithm.

The target is the EED-only algorithm described by [IMOD's nad_eed_3d manual](https://bio3d.colorado.edu/imod/doc/man/nad_eed_3d.html), based on [Frangakis & Hegerl, 2001](https://doi.org/10.1006/jsbi.2001.4406). The application's existing parameter contract is retained: positive K as a multiple of volume SD, 1–200 iterations, structure-tensor sigma 0, time step 0.1, full XYZ processing. CED/hybrid filtering, tensor smoothing at nonzero sigma, alternative time steps and the original CLI's file-format/iteration-series switches are not exposed by this option. This is a native implementation of the algorithm used by the option, not a wrapper around the original CLI.

Centered XYZ differences form the symmetric structure tensor. A fixed-size Householder/implicit-shift QL eigensolver recovers its eigenvectors. The two larger-eigenvalue directions receive the EED conductance `1 - exp(-3.31488 / (gradient/K)^16)`; the smallest direction receives unit conductance. Transforming this diagonal matrix back yields six tensor fields. Each explicit step evaluates six axis neighbors and twelve face diagonals from the previous iterate. No image plane is filtered independently.

Compatibility includes periodic extension while estimating derivatives, the original upper-Z north/front versus north/back diagonal convention, tensor float32 rounding, and float32 voxel evolution. The unsmoothed tensor is nearly rank one: mathematically equivalent reassociation of floating-point expressions can rotate its two small-eigenvalue directions and change subsequent iterations. Do not replace these expressions or the eigensolver with an approximate shortcut without rerunning the original-program comparisons. The upper-Z convention is retained for numeric compatibility and is not asserted to be an ideal physical boundary condition.

The Rust implementation uses the published mathematical construction and independently written array/offset operations and eigensystem code. No upstream C source, GPL program, or LGPL library is vendored or linked. The original installed IMOD 5.1.3 is used only as a development oracle. Reference-source browsing and intermediate numerical probes are retained outside the repository in the acceptance evidence directory.

`tests/fixtures/nad3d` contains synthetic inputs and numerical oracle outputs with checksums and exact reference arguments. The actual `prepare()` path compares all voxels with these outputs while `IMOD_NAD_PATH` deliberately points to a nonexistent program. Other tests cover true Z coupling, cancellation, invalid/extreme input, parameter cache changes, all-Z preview/export consistency, unchanged input files, calibration and cache cleanup. The normal Pro build requires no new dependency.

At implementation acceptance, all 18 synthetic reference volumes matched exactly. A real 128×128×32 cryo-ET crop also matched IMOD exactly at K/SD and iteration pairs `(0.1,5)`, `(0.8,5)`, `(3.5,2)` and `(0.1,20)`, including every boundary plane. These are observations on the tested IMOD 5.1.3 arm64 build; they are not a guarantee of bit identity with every compiler or later upstream version. Noise reduction and preservation of biological signal depend on parameters; output agreement is not biological validation. Full records: `/Volumes/samsung/pro-test/native-nad-rust-20261109`.
